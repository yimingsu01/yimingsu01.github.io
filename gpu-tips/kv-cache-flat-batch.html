How a batched forward pass writes the KV cache

gpu-tips, note 1. November 19th, 2026.

An inference engine such as vLLM runs many requests in one forward pass. The requests have different lengths, and each request has its own KV cache. This note shows how the new tokens of all requests go into one batch, and where the keys (K) and values (V) of each token go.

Each layer writes the K and V of a new token directly into the cache blocks of that token's request. No step cuts the KV out of an output tensor after the pass.

The example

Three requests are in the engine at the same time.

RequestTokens in the cacheNew tokens in this stepReason
A5,0001A generates its next token.
B8001B generates its next token.
C02,000C is a new prompt. All its tokens are new.

This step has 2,002 new tokens.

The flat batch

The engine lays out the new tokens as one flat batch, [A, B, C1, C2, …, C2000]. The input to each layer has 2,002 rows, one row for each new token.

The cache is one large pool of blocks on the GPU, and all requests share it. In vLLM, one block holds the K and V of 16 tokens by default. A slot is the place of one token in a block. The slot number is the block number × 16 + the position in the block.

The engine passes two index tables with the batch. The names are the names that vLLM uses.

Slot mappingFor each row, the cache slot where its K and V goWrite

The two outputs

A forward pass has two outputs. The engine cuts only one of them.

  • The KV cache is never cut. Each layer writes it in place in step 2. The slot mapping puts each K and V in the blocks of the correct request.
  • The final hidden states are cut. After the last layer there are 2,002 rows. The engine takes one row for each request. These are row 0 for A, row 1 for B and row 2001 for C, which is the last prompt token of C. Each of these 3 rows gives the scores for the next token of its request. The engine discards the other 1,999 rows of C. They were necessary only to make the KV of C.

Why the attention is not one square matrix

A plain batched attention needs all requests at the same length, which is 5,001 here. B then carries 4,200 empty positions and C carries 3,001. Approximately half of the 15,003 positions are empty.

The block table removes the empty positions. Each row reads only the blocks that exist for its request. Thus requests of very different lengths share one batch, and no position is empty.

What follows from the block pool

Prefix hits on the GPU

Let request D run at the same time as C. The first 1,024 tokens of the two prompts are the same. These tokens fill 64 blocks, and the 64 blocks are in the pool already. The engine puts those blocks into the block table of C and removes those 1,024 rows from the batch. It copies nothing and computes nothing for these tokens.

A hit always has a whole number of blocks. The engine identifies each full block by a hash of its tokens and of all the tokens before it.

Blocks shared by reference

The 64 blocks are now in two block tables. Each block has a reference count, which is 2 here. The engine releases a block only when no request uses it. A released block keeps its data until the engine needs the space. Thus a later request with the same prefix can still get a hit.

LMCache

LMCache enters at the same place. It copies a loaded chunk into pool blocks, and those blocks go into the block table of the request. A layer reads these blocks in the same way as all other blocks.
